# Candidate payment flow

This is an illustrative target following the developer's approval of PayMongo as the planned gateway and the developer-reported adviser approval/panel recommendation. Detailed architecture and method-specific decisions remain subject to review. Provider behavior claims are referenced in `01-official-sources.md`.

1. Customer chooses PayMongo for either delivery or pickup. Route card, GCash, Maya, and QR Ph through Hosted Checkout v2; route enabled Direct Online Banking methods through the documented Payment Intent redirect flow. Do not imply DOB is available in Hosted Checkout. Existing server validation rechecks cart, fulfillment, and amount. Customers do not upload receipts; request a provider email receipt only where the selected API documents that feature and the checkout email is valid.
2. Persist the pending order through the existing order workflow, keeping order status distinct from payment status. Existing placement consumes stock immediately and removes the cart; treat this as a 24-hour stock hold unless a paid/uncertain payment prevents closure.
3. Commit a local flow and operation identity with the order before provider dispatch. Outside the retried database transaction, create the Checkout Session or complete the documented bank flow: create Payment Intent, create bank Payment Method, attach it, then obtain its redirect. Verify authentication and idempotency support for each endpoint; persist stable references before handing off. Timeout after dispatch is an unknown outcome requiring recovery of that operation. No replacement flow may start while its predecessor could succeed. Fees remain absorbed by default. See `10-readiness-audit.md` for creation, method-switch and crash contracts.
4. Browser navigates to hosted URL. Return/success/cancel pages show locally known status only; a return does not verify payment.
5. Receive the flow-specific event: `checkout_session.payment.paid` for Hosted Checkout; documented `payment.paid` / `payment.failed` for banking. Check request limits, verify signature over exact raw bytes with the configured environment secret, then validate mode/envelope. Do not let an untrusted mode field select an unauthorized environment.
6. Insert/deduplicate a minimal authenticated inbox entry and commit it before responding promptly with HTTP 200 JSON. If durable persistence fails, return a retryable failure. For authenticated unsupported event types, acknowledge and ignore. Event receipt is not completion; duplicate delivery must not suppress recovery of a previously unprocessed entry.
7. A worker or inbox sweeper claims durable pending entries. Validate provider identity and known order/flow association, exact paid amount/currency/mode and current locked local state. Select the actual matching successful payment from a Checkout payments array, not its first entry or parent session status. If event evidence is incomplete or mismatched, retrieve trusted state or quarantine. Unknown associations may be an early webhook racing provider-reference persistence; retain for bounded reconciliation, never attach solely by customer-controlled metadata.
8. Apply payment success and processed-event marker atomically with the appropriate domain transition, deduplicating both event and provider payment identity. A crash after commit must replay without reapplying effects. Verified payment does not move shipment, complete pickup, deduct stock again, or record a sale. Notification delivery follows the existing after-commit behavior and its documented recovery limits. A durable inbox sweep must recover enqueue failures and abandoned worker claims.
9. When PayMongo expires a payment method/action, use only the status/event documented for that specific method and provider flow; do not assume Payment Acceptance event names apply to Checkout Sessions. Allow retry in the same active flow where supported and within the 24-hour merchant order window. Do not interpret method expiry as order cancellation, Checkout Session/Payment Intent closure, or stock-release authorization.
10. At 24 hours from order placement, retrieve/reconcile the latest provider state. If paid, follow the payment transition; if pending, processing, or unknown, retain the order and stock hold and retry/escalate. Otherwise close the provider flow using its documented action and verify the resulting terminal state. PayMongo sends no Checkout Session-expiry webhook. Only after confirmed provider closure and no unresolved payment may the existing cancellation transition restore stock.
11. Record provider gross amount, fee, and net amount separately from the order's base payable amount. Do not treat the customer-paid fee as order merchandise revenue.
12. Automated refunds are excluded from first release. A paid-order cancellation/refund request requires administrator review and separate authorization using the then-current provider-eligible process. If payment evidence conflicts with a cancelled order, do not fulfill automatically; route to reconciliation/support.

## Failure paths and cancellation

Use the state table, operations ownership, retry limits and rollout contracts in `10-readiness-audit.md`. The same reconciliation/closure boundary applies to customer cancellation, administrator cancellation, scheduled cutoff, and method switching. A browser cancel return only displays state. A creation timeout is not proof no payable object exists; a local closing flag does not invalidate the provider URL. No provider network request belongs inside a retried database transaction.
